# Project Audit

Audit date: 2026-10-23. Findings below were checked against the current PHP source, local Apache/MySQL runtime, live `realestatephp` database, and local browser. This is a focused audit, not a certification of every legacy page.

| Severity | Verified finding and status | Affected files | Recommended fix / disposition |
| --- | --- | --- | --- |
| **High — fixed** | Seller appointment, offer, and rental-inquiry actions previously lacked CSRF validation and did not always bind the changed record to the seller-owned property. Authenticated HTTP tests now reject missing CSRF tokens with 403, reject cross-property record IDs with 404, and leave the other owner’s records unchanged. | `view_appointments.php`, `view_offers.php`, `view_rental_interest.php` | Keep mutations POST-only, validate the session token, and scope every update to both the record and authorized property. |
| **High — fixed** | The `user.email` column had no unique index in the dump or live database, so concurrent registrations could bypass the application’s duplicate pre-check. The current database had no duplicate email groups; the unique constraint and migration are now applied, and registration handles duplicate-key errors. | `register.php`, `DATABASE FILE/realestatephp (3).sql`, `DATABASE FILE/migrations/20261023_add_user_email_unique.sql` | Check existing deployments for duplicates, resolve them without deleting user data, then apply the migration once. |
| **Medium — fixed** | Appointment acceptance previously attempted SMTP delivery regardless of the documented `APP_SEND_EMAIL` opt-in and loaded mail configuration on every request. It now sends only when explicitly enabled; missing credentials and send failures are logged and reported without undoing the appointment decision. SMTP delivery itself was not tested. | `view_appointments.php`, `README.md` | Configure `secrets.php` and `APP_SEND_EMAIL=true` only where SMTP is intentionally enabled; run a sandbox/test-mail check before relying on delivery. |
| **High — blocked by design** | Sale/rental checkout and return endpoints respond with HTTP 503. No verified provider order, webhook/signature validation, idempotency, or transaction workflow is available. | `create_checkout_session_sale.php`, `create_checkout_session_rental.php`, `payment_success_sale.php`, `payment_success_rental.php` | Keep payments disabled. Define payment terms and implement/test server-verified provider events before enabling checkout. |
| **Medium — outstanding data quality** | The live database and home/listing pages contain sample titles such as `test` and `tgr`, with visibly implausible prices or property dimensions. These records were not edited or removed. | `DATABASE FILE/realestatephp (3).sql`, `property_listings` data | Replace demo records with reviewed, realistic fixtures before presenting the site publicly; add validation for plausible listing values. |
| **Medium — not verified for deployment** | The optional Flask/Gemini chatbot has no runtime validation because no usable Python interpreter is installed; provider configuration was not verified. | `chatbot_server.py`, `requirements.txt`, `.env.example` | Install Python, configure a least-privileged read-only DB user and Gemini key, then test the endpoint and monitor/rate-limit it before exposure. |
| **High — implemented and role-flow tested** | Public registration supports Buyer and Agent using the existing `user.role` field; invalid/admin role registration creates no account. Buyers return to the marketplace after signing in, while Agents and Super Admins receive their respective dashboards. Protected pages enforce role access server-side. | `register.php`, `login.php`, `auth.php`, `include/header.php`, `seller_dashboard.php`, `agent_dashboard.php`, `favorites.php`, `Bought_Propertyes.php` | Keep role allowlisting and backend checks; add automated tests for role redirects and authorization boundaries. |
| **High — implemented and owner-scoped** | Seller and Agent listing management queries require the current user's listing ownership. Agent access is not automatically extended to listings owned by other users; an Agent's attempt to edit a Seller-owned listing returned 404. Seller create/edit/status/delete and Agent create/read/delete were exercised with isolated records. | `my_properties.php`, `submitproperty.php`, `edit_property.php`, `include/managed_dashboard.php` | If Agent assignment is later introduced, model it explicitly with a relationship table and update authorization checks; do not infer assignment from role alone. |
| **Medium — fixed in this pass** | The shared header overflowed the viewport on the registration page at mobile width; the navigation now wraps for narrow screens. A further responsive check is recorded in `TEST_REPORT.md`. | `css/role-themes.css` | Retest any future header changes at mobile widths and on authenticated navigation variants. |
